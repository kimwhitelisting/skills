# 저장과 중단 후 복귀

## 계정 저장과 결제 요구사항

BENTO-ACCOUNT-SPEC-001 · 2026-11-06 · **요구사항 기록이며 미구현**. 사용자는 로그인한 계정에 진행을 저장하고 결제 기능도 제공하려는 의도를 확인했다. 아래는 냠냠졸졸의 후속 설계·구현 기준이며 아직 구현되지 않았다. 상품 구성·서버 공급자·비용은 미확정이다.

| 구분 | 현재 구현 | 목표·미결정 사항 |
|---|---|---|
| 진행 저장 | localStorage snapshot + 같은 기기의 Native Preferences, 복구 원본/JSON 내보내기. 로그인·서버 저장 없음 | 인증된 계정에 서버 저장하고 재설치·기기 변경 후 복원. 로컬 저장·복구는 보조 캐시/장애 대응 수단 |
| 상점·결제 | 플레이로 얻은 하트로 게임 아이템 구매. 실제 스토어 결제/IAP 없음 | 결제 유형은 “아직 미정 — 설계부터 보고 결정”으로 답변받음. 유료 재화 도입을 가정하지 않음 |
| 운영 선택 | 광고 + 광고 제거는 기존 계획으로 아직 미구현 | 로그인 방식·백엔드 공급자·오프라인/게스트 허용·기존 저장 이전 정책 미결정. 길목에 같은 방식을 적용할지도 별도 결정 |

후속 구현·출시의 완료 기준:

- **계정별 저장:** 서버가 인증된 계정의 저장 접근 권한을 확인한다. 계정 전환/로그아웃 때 화면·로컬 캐시·전송 대기 작업을 계정별로 분리하여 다른 계정의 기록을 읽거나 덮어쓰지 않아야 한다.
- **동기화 충돌:** 저장 버전과 서버 반영 상태를 구분하고 여러 기기·끊긴 네트워크의 재전송/오래된 저장 충돌 처리 규칙을 정한다. 로컬 저장만 성공한 상태를 계정 저장 완료라고 표시하지 않는다. 충돌 시 원본을 보존하고 선택/병합 정책을 적용한다.
- **구매 검증과 귀속:** 스토어의 거래 상태를 서버에서 검증하고 앱 계정에 연결한다. 스토어·앱·거래 식별자로 동일 거래의 중복 알림/재시도/복원에도 한 번만 권리나 재화를 지급한다. 클라이언트의 결제 성공 표시만으로 지급하지 않는다. 다른 앱 계정으로 같은 구매를 옮길 수 있는지는 별도 정책으로 정한다.
- **유료 권리 분리:** 결제 원장과 권리 상태는 일반 진행/도감 저장과 분리한다. 유료 재화를 도입한다면 유료 잔액·지급/소비 내역을 서버에서 관리하고 기존 로컬 `hearts`·`owned`·snapshot·복구 JSON을 유료 소유권이나 잔액의 증거로 신뢰하거나 그대로 가져오지 않는다. 플레이 보상의 이전/검증 정책도 별도로 정한다.
- **구매 복원·환불:** 복원은 검증된 거래/현재 권리 상태를 재조회하며 중복 지급하지 않는다. 결제 대기·실패·환불·권리 철회와, 구독을 선택할 경우 만료 상태를 서버 원장 및 앱 표시와 대조한다. 소비성 상품을 비소비성 권리처럼 재지급하지 않는다.
- **게스트·기존 저장 이전:** 게스트 이용과 계정 연결, 기존 진행/무료 하트/도감의 가져오기·충돌·재가져오기 처리는 아직 미결정이다. 결정 전에는 기존 로컬 기록을 삭제하거나 자동 업로드하지 않는다.
- **운영자 백업:** 서버의 백업 보관·접근·복원 시험·계정 삭제 처리 기준을 따로 정한다. 기기 OS 백업이나 사용자가 내보낸 JSON은 운영자 서버 백업과 별개이며 계정 저장/결제 원장의 대체 수단이 아니다.
- **검증:** 재설치, 다른 기기 로그인, 계정 전환, 동시 기기 수정, 네트워크 단절/재연결, 결제 대기/취소, 환불/철회, 동일 거래 중복 전달과 구매 복원을 시험한다. 진행 복원·계정 간 격리·중복 지급 없음·원장 일치를 각각 확인하고 스토어 시험 환경과 실기기 결과를 구분한다.

현재 개인정보 초안은 실제 로컬 구현을 설명한다. 계정/서버/결제 설계가 결정되고 구현되면 수집 항목·이용 목적·사업자·보관/삭제·복원 범위와 스토어 신고를 해당 출시 전에 갱신해야 한다. 아래는 계속 **현재 로컬 구현**의 기술 기록이다.

상품 비교·계정 연결·동기화·구매 복원·비용 후보와 결정 순서는 [ACCOUNT-DESIGN.md](ACCOUNT-DESIGN.md)를 설계 원본으로 따른다. 상품과 공급자가 선택된 것으로 취급하지 않는다.

## BENTO-STABLE-001의 저장 형식

- 기존 `bento-life:run:v2`, `bento-life:dex:v1`, `bento-life:prefs:v1` 키는 삭제하지 않는다. 새 snapshot이 없으면 이 값을 검증해 읽는다.
- 본 게임의 새 저장은 `bento-life:snapshot:v1` 한 JSON에 진행·도감/하트·설정을 함께 쓴다. 하나의 localStorage 교체가 성공해야 세 값이 함께 새 시점으로 바뀐다. GameState의 `version: 2`는 유지한다.
- 유효한 snapshot이 생기면 그 값을 우선한다. 기존 키는 이전 원본으로 남으며 최신 snapshot과 계속 동기화되는 복제본이 아니다.
- 이전 유효 snapshot은 `:last-good` 하나에 보관한다. 이를 전체 플레이 이력 백업이나 클라우드 동기화로 설명하지 않는다.
- 구버전 앱은 새 snapshot을 모른다. 구버전 코드로 운영을 되돌리기 전에 최신 snapshot을 보존하고 호환 변환을 준비해야 한다. HTML만 이전 버전으로 바꿔도 최신 진행이 그대로 표시된다고 보장하지 않는다.

## 실패·손상·Native 복구

- 저장 실패는 화면의 안내와 `저장 다시 시도`로 알린다. 입력과 아침 타이머/등굣길 진행을 멈추고 메모리의 최신 저장 후보를 재시도한다. 앱을 닫으면 아직 성공하지 못한 후보는 잃을 수 있으므로 닫기 전 재시도가 필요하다.
- 읽기 실패는 데이터 없음으로 간주하지 않는다. 확인되지 않은 원본을 기본값으로 덮어쓰지 않는다.
- JSON과 사용되는 중첩 구조·ID/값 범위를 검증한다. 손상된 원본은 `:recovery:` 키에 내용별로 보관하고, 같은 원본의 재시작/재시도는 중복 보관하지 않는다. 다른 손상 원본을 자동 삭제하지 않는다. 앱 재실행 후에도 설정의 `보관한 저장 원본 내려받기`에서 이 게임의 보관 원본을 내려받을 수 있다. 다른 서비스의 저장 키는 내보내지 않는다.
- 정상 Native 백업 또는 last-good을 복구할 때도 손상 원본부터 보존한다. 원본 보존에 실패하면 진행을 막고 내려받기 경로를 제공한다. 복구할 정상 데이터가 없으면 조용히 새 게임으로 바꾸지 않는다. 사용자가 `백업을 남기고 새로 시작`을 선택하고 범위를 읽은 뒤 두 번째 확인을 해야 새 저장을 만든다. 확인 시 다시 진단하여 정상 Native/last-good 백업을 찾으면 초기화 대신 복구를 우선한다. 원본 보관에 실패하면 초기화를 거부한다. 구형 진행만 손상된 경우 확인된 도감/하트와 설정은 유지한다. 통합 snapshot이 손상된 경우 전체 초기화 범위를 명시한다. Native 원본을 읽지 못해 확보하지 못한 상태에서는 이 초기화도 허용하지 않는다.
- Native Preferences 읽기·보관·복원 쓰기 중 신뢰할 원본을 확인하지 못하면, 백그라운드 저장도 중단한다. 정상 Native 원본을 확인하기 전 오래된 로컬 fallback으로 Native를 덮지 않는다.
- Native 쓰기는 순서대로 실행하고 비동기 오류를 잡는다. `flushStorage()`는 큐의 저장 완료를 기다린다. 앱 백그라운드 전환 시 저장/flush를 요청하지만 OS 강제 종료까지 막거나 종료 후 Promise 완료를 보장하지는 않는다.
- Native Preferences는 같은 기기 안의 보조 저장이다. 앱 삭제·기기 교체를 견디는 서버 계정 백업으로 설명하지 않는다.

- 현재 메모리의 진행 형식이 잘못되어 저장할 수 없으면 이전 정상 저장을 유지한다. 재시도 때 현재 진행을 다시 검증하며, 계속 실패하면 사용자가 원본을 내려받거나 두 단계 확인 후 저장된 진행으로 돌아갈 수 있다. 이 경우 저장되지 않은 변경이 사라진다는 문구를 표시한다.

## 화면 체크포인트

- 아침의 재료, 선택 탭, 마지막 재료, 남은 시간을 진행과 함께 저장한다. 타이머는 초 단위로, 선택·이동·pagehide/백그라운드 시에도 기록한다.
- 이벤트의 스탯 처리는 이미 끝난 상태와 결과 문구를 함께 보관한다. 재접속에서 결과 문구를 다시 보여 주되 이벤트 효과를 다시 적용하지 않는다.
- UI checkpoint는 동일한 나이·날짜·단계·활성 이벤트일 때만 쓴다. 과거 checkpoint와 잘못된 값을 다음 날에 적용하지 않는다. 이전 버전 저장에 checkpoint가 없으면 해당 엔진 단계에서 진입한다.
- 등굣길은 별도 version1 checkpoint로 좌표·점수·경계심·남은 시간·위기/방해 이벤트·도구 사용·로그를 저장한다. 0.5초 간격 및 화면 전환·백그라운드 시 기록한다.
- 등굣길 복귀는 일시정지 상태이고 누르고 있던 걷기 입력은 해제한다. `이어서 걷기`를 누른 뒤 진행한다. 최종 결과 상태도 복원하며 저녁 정산은 한 번만 적용한다.
- 구버전의 등굣길 저장에는 위치가 없다. 이 경우 시작 지점부터 이어간다는 안내를 먼저 표시한다. 이것을 과거 위치 복원 성공으로 보고하지 않는다.
- 강제 종료 직전의 마지막 프레임까지 보장하지 않는다. 아침은 마지막 저장 시점, 등굣길은 마지막 0.5초 checkpoint 이후 진행이 일부 되돌아갈 수 있다.

## 검증

`npm test`는 게임 규칙·2000판 자동 플레이와 `tests/persistence.test.ts`를 실행한다. 저장 회귀에는 quota 실패/전체 snapshot 재시도, 손상 구조, Native authority 읽기·보관·복구 실패, 백업 읽기 재시도, 원본 중복 보관, 직렬 Native 쓰기, 체크포인트 JSON 왕복·잘못된 날짜 거부, 등굣길 단계 복원, 전환 직후 연속 탭 보호가 포함된다.

합성 실패 테스트는 메모리 저장소·가짜 Native API로 수행한다. 실제 기기의 디스크 장애·OS 강제 종료를 재현했다는 뜻이 아니다. UI와 실기기 결과는 [PLAYTEST.md](PLAYTEST.md)에 별도로 기록한다.

## 복구 원본 파일 내보내기

- 웹은 Blob 다운로드를 요청한다. Native 진입점은 공식 Filesystem8.1.5/Share8.0.3 어댑터를 등록하고, `Directory.Cache`의 `nyamnyam-save-recovery.json` 한 파일에 UTF-8로 쓴 뒤 OS 공유 창을 연다. 게임 저장·복구 원본 키는 변경하거나 삭제하지 않는다.
- 사용자가 내보내기를 누른 경우에만 실행하며 파일 작성부터 공유 창 반환까지 중복 요청을 막는다. 캐시 파일은 다음 요청에서 덮어쓸 수 있고 OS가 정리할 수 있으므로 장기 백업이 아니다. 보관할 위치나 공유 앱은 사용자가 고른다.
- 취소와 파일/공유 실패를 안내하고 다시 시도할 수 있다. 공유 창 반환이나 브라우저 다운로드 요청이 실제 파일 보관 완료를 증명하지 않으므로 완료로 표시하지 않는다. 선택한 위치의 JSON을 직접 확인해야 한다.
- 외부 저장소 권한을 추가하지 않는다. iOS Privacy Manifest에 기존 UserDefaults 사유와 함께 FileTimestamp `C617.1`을 선언한다. 공식 근거(2026-11-06 확인): [Filesystem v8](https://capacitorjs.com/docs/apis/filesystem), [Share v8](https://capacitorjs.com/docs/apis/share).
- 모의 어댑터 테스트는 읽기/파일쓰기/공유 실패·취소·동시 요청·재시도·정확한 JSON 전달을 검증한다. 실제 Android/iPhone의 공유 대상 선택·취소·Files 저장 및 저장된 JSON 확인은 별도이며 아직 미검증이다.
