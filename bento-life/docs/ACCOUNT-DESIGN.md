# 냠냠졸졸 계정 저장·결제 설계안

BENTO-ACCOUNT-DESIGN-001 · 2026-11-06 · 기준 `c73c1e0` · **설계 제안, 미구현**.
Owner는 결제 유형을 “아직 미정 — 설계부터 보고 결정”으로 답했다. 상품·공급자·예산은 확정하지 않았다.
기존 요구사항은 [STORAGE.md](STORAGE.md#계정-저장과-결제-요구사항), 실제 로컬 구현은 같은 문서의 BENTO-STABLE-001 이하를 따른다.

## 1. 먼저 만들 범위

**권장 순서: 계정 저장으로 무료 테스트 → 진행·복원 검증 → 상품 한 종류 선택 → 결제 시험 → 출시 판단.**
현재 앱은 로그인·서버·실제 결제 없이 로컬에 저장하며, 하트 상점은 플레이 보상만 사용한다. 로컬 보호 작업은 이를 안정화한 것이지 계정 저장을 구현한 것이 아니다.
첫 단계는 Apple/Google 로그인 후보, 계정별 진행 저장, 기기 변경 복원, 충돌 안내, 계정 삭제까지다. 결제·광고 SDK는 상품 선택 후 별도 단계에 둔다.
기존 무료 하트·상점 아이템·이미 얻은 콘텐츠를 소급해서 유료로 전환하지 않는다. 게스트 체험은 선택 사항이며 첫 단계의 필수 요건은 아니다.

## 2. 수익화 선택지

| 선택 | 사용자가 받는 것 | 개발·운영 부담 | 제안 |
|---|---|---|---|
| 광고 + 일회성 광고 제거 | 기본 무료 플레이, 구매 후 정해진 광고 제거 | 광고 SDK·동의·노출 정책과 비소비성 구매 복원 필요. 어떤 광고까지 제거할지 명시 | 광고를 실제 도입하기로 할 때 후보. 현재 광고 없음 |
| 신규 꾸미기/이야기 팩 | 기존 무료 콘텐츠와 구분되는 새 팩 영구 이용 | 비소비성 권리·복원·환불 및 새 콘텐츠 제작. 이야기 팩은 밸런스 검토 추가 | 첫 유료 기능은 소규모 신규 꾸미기 팩 한 종류 우선 검토 |
| 유료 하트 | 구매한 소비성 재화 사용 | 서버 잔액·지급/소비 원장·중복 지급/환불·무료 재화 구분·밸런스 관리 | 초기 범위에서 보류 권장. 기존 하트와 합쳐 신뢰하지 않음 |
| 구독 | 기간 중 지속적으로 제공되는 혜택 | 갱신·만료·유예·환불과 매기간 혜택 공급 운영 | 반복 제공할 가치가 정해진 뒤 검토 |

초기 복잡도를 줄이는 권장안은 광고 없이 계정 저장을 먼저 시험하고, 필요하면 새 꾸미기 팩을 추가하는 것이다. 수익성이나 구매 전환을 보장하는 제안은 아니며 가격·상품명은 미정이다.

## 3. 로그인과 계정 연결

1. 첫 로그인에서 서버가 앱 계정 UUID를 부여하고 인증 공급자의 검증된 identity에 연결한다. 표시 이름·이메일을 저장/구매의 주 식별자로 쓰지 않는다.
2. 다른 기기에서는 같은 로그인 수단으로 같은 계정을 연다. iPhone/Android 모두에서 사용할 로그인 조합과 로그인 복귀 URL을 실제 기기로 확인한다.
3. 다른 수단을 연결하려면 로그인된 계정의 설정에서 명시적으로 시작하고 추가 공급자 인증을 마친다. Apple 비공개 이메일과 Google 이메일이 달라도 이메일 문자열로 같은 사람이라고 추정하지 않는다.
4. 이미 각각 진행이나 구매가 있는 두 앱 계정의 통합은 별도 문제다. 양쪽 계정의 소유 증명·충돌 선택 없이 저장·구매를 합치지 않는다. 첫 버전은 자동 통합을 제공하지 않는 안을 권장한다.
5. 로그아웃/계정 전환은 이전 계정 화면·캐시·전송 대기 작업을 분리한다. 이전 요청의 늦은 응답이 새 계정에 적용되지 않게 계정과 로그인 세대를 확인한다.
6. Native 로그인 토큰은 플랫폼 보안 저장소를 사용하는 검증된 어댑터에 둔다(패키지 미선정). 게임 snapshot·복구 JSON·클라우드 게임 저장에는 토큰을 넣지 않는다. 서버 관리자 키와 스토어 비밀도 클라이언트에 배포하지 않는다.

Supabase는 검증된 identity의 동일 이메일 자동 연결과 수동 연결 기능을 설명한다. 이 동작을 보안 결함이라고 단정하지 않는다. **인증 identity 연결과 게임 저장/구매 병합은 구분**하며, 공급자의 실제 동작이 제품 연결 규칙에 맞는지 먼저 시험한다. 자동 연결을 임의로 끌 수 있다고 가정하지 않는다. 양립하지 않으면 로그인 구성이나 Auth 후보를 다시 선택한다. [공식 identity 연결 문서](https://supabase.com/docs/guides/auth/auth-identity-linking)

## 4. 저장 흐름과 기존 기록 이전

- 계정 클라우드 저장은 사용자의 기기 변경을 위한 데이터다. 로컬 캐시/복구 원본, OS 백업, 운영자의 서버 재해 복구 백업과 각각 구분한다.
- 로그인 뒤 서버 저장 유무와 기기의 기존 진행을 비교한다. 기존 기록이 있으면 이름·진행 시점·도감 등 요약과 계정을 보여 주고 가져오기 동의를 받는다. 취소하면 업로드·삭제하지 않는다.
- 이전은 검증한 무료 진행 snapshot 하나를 선택해 복사한다. 서버 기록이 있으면 양쪽을 보존하고 어느 진행을 사용할지 선택한다. 하트 합산·아이템 집합 합치기·유료 권리 생성은 하지 않는다.
- 계정별 이전 작업 ID와 원본 지문을 기록해 응답 유실·재실행에도 같은 이전이 반복 지급으로 이어지지 않게 한다. 완료 뒤에도 기존 로컬 원본을 자동 삭제하지 않는다.
- 구조 검증은 잘못된 저장을 차단하지만 조작된 무료 진행의 진위를 증명하지 않는다. 오프라인 무료 하트의 무결성이나 서버 기반 부정행위 차단을 완성했다고 주장하지 않는다.
- 게스트를 제공한다면 “이 기기에만 저장됨”을 표시하고 구매는 로그인 뒤에만 허용하는 안을 권장한다. 게스트 기록의 계정 연결·이전도 위 선택 절차를 따른다.

## 5. 동기화와 최소 데이터 경계

앱은 로컬 저장 후 `계정에 저장 중 / 계정에 저장됨 / 기기에만 저장됨 / 충돌 확인 필요`를 구분한다. 서버 응답을 받기 전에는 계정 저장 완료로 표시하지 않는다.

| 서버 데이터 제안 | 핵심 규칙 |
|---|---|
| 계정 및 인증 identity 연결 | 안정된 UUID, 서버 검증, 계정별 접근 제어 |
| 게임 저장·이전 기록 | 계정, 스키마 버전, 저장 revision, 본문, 서버 시각, 작업 ID |
| 충돌 보관본 | 두 진행과 각 기반 revision 보존. 사용자 선택 전 자동 덮어쓰기 금지 |
| 결제 거래·권리 | 게임 JSON과 별도. 검증된 거래/권리만 서버가 갱신 |
| 유료 재화 원장 | 상품 선택 시에만 추가. 지급·소비·취소를 서버 거래로 처리 |

쓰기 요청은 읽었던 revision과 새 내용을 보낸다. 서버는 같은 revision일 때만 한 트랜잭션으로 교체·증가시키는 비교 후 갱신(CAS)을 수행한다. 기기 시각이 늦다는 이유로 덮어쓰지 않는다.
전송 대기함(outbox)은 계정·작업 ID·기반 revision을 가진다. 같은 요청 재시도는 한 번만 반영하고, 로그인 만료면 중단 후 같은 계정 인증 뒤 재개한다. 새 계정 자격으로 이전 요청을 재전송하지 않는다.
두 기기가 같은 revision에서 수정하면 하나만 바로 반영하고 다른 하나는 충돌로 보관한다. 선택 후에도 선택하지 않은 원본을 정해진 복구 기간 보존한다. 보존 기간·용량·사용자 삭제 정책은 구현 전 확정한다.

## 6. 결제 귀속·복원·오프라인

- 구매 버튼 전에 앱 로그인을 확인하고 구매가 귀속될 계정을 보여 준다. 앱 계정 UUID를 구매 서비스와 일관되게 연결하되 키·영수증 검증 비밀은 앱에 넣지 않는다.
- 스토어 거래를 서버에서 검증한 뒤 권리를 반영한다. 결제 대기/취소는 지급하지 않는다. Android 구매 토큰 등 검증된 식별자와 앱·스토어·시험/운영 환경을 구분하고, 거래/갱신/상태 이벤트별 중복 키를 설계한다. 주문번호나 알림 도착 순서만 믿지 않는다. [Google Play 보안 권고](https://developer.android.com/google/play/billing/security)
- 거래 저장과 권리/잔액 반영은 서버에서 중복 없이 처리한다. 웹훅은 인증하고 중복·순서 역전을 허용하는 구조로 재조회·대조한다. 플랫폼별 acknowledge/consume 및 서버 장애 재처리도 결제 단계에서 검증한다.
- 구매 복원은 현재 권리를 확인하는 동작이다. 이미 소비한 상품을 새로 지급하지 않고, 로컬 `hearts`·`owned`·복구 JSON을 유료 증거로 사용하지 않는다. 다른 앱 계정으로 구매를 자동 이전하지 않는 안을 권장한다.
- RevenueCat의 **기본값은 계정 간 이전**이다. `Keep with original App User ID` 후보는 구매 전 로그인 필수이며, 다른 계정의 복원뿐 아니라 같은 영수증의 새 구매도 거절할 수 있다. 이를 기본 보장으로 오해하지 않는다. 결제 진입 전에 기존 귀속을 확인 가능한 범위에서 점검하고 원래 계정 복구/문의 경로를 제공한다. 모호하면 새 결제를 유도하지 않는다. [공식 복원 동작](https://www.revenuecat.com/docs/projects/restore-behavior)
- 새 기기·플랫폼에서 권리를 적용할 범위는 상품 ID 대응과 양 스토어 조건을 확인해 확정한다. 같은 이메일이나 같은 스토어 로그인만으로 앱 계정이 같다고 간주하지 않는다.
- 환불·철회·구독 만료를 서버의 현재 상태와 대조해 권리를 회수한다. 이미 사용한 소비성 재화의 환불 처리 기준은 상품 선택 전 정한다. 과거 성공 이벤트의 재도착으로 철회한 권리를 되살리지 않는다.
- 오프라인 무료 진행은 로컬에 계속 쓸 수 있다. 유료 비소비성 권리는 마지막 서버 확인값의 캐시 허용 기간을 별도로 정한다. 기간 경과 시 안내하고 새 구매/유료 소비는 온라인 검증 전 허용하지 않는 안을 권장한다. 캐시의 오래된 권리를 영구 권리로 취급하지 않는다.

## 7. 기술 후보와 비용

**후보:** 기존 Node22·TypeScript·Capacitor8을 유지하고 Supabase Auth/Postgres로 계정/저장을 구현한다. 결제 상품 선택 후 RevenueCat의 공식 Capacitor 연동을 검토한다. 어느 공급자도 아직 선정·생성·설치하지 않았다.
MacBook은 개발·빌드 기기다. 출시 앱의 계정/저장 API는 Mac의 잠자기·오프라인과 독립적으로 호스팅하며, Tailscale 미리보기는 개인 시험용이고 플레이어용 운영 서버가 아니다.
Supabase는 관계형 데이터의 revision 갱신·거래/권리 분리와 계정별 접근 규칙을 표현하기 쉽다는 이유로 제안한다. RLS를 켜고 계정 소유 행만 허용하며 관리자 권한 키는 서버에만 둔다. 유료 테이블은 앱의 직접 쓰기를 금지한다. [RLS 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)
RevenueCat은 스토어별 구매 상태 처리 부담을 줄일 후보지만 계정 저장 서버를 대체하지 않는다. 공식 Capacitor 연동이 있다는 사실과 현재 Capacitor8에서 특정 SDK 버전이 검증됐다는 주장은 다르다. 정확 버전 호환·native 빌드·복원 설정 시험이 먼저다. Android 현재 `singleTask`와 공식 권장 `standard/singleTop`의 차이는 뒤로가기/로그인 복귀까지 함께 검증한다. [Capacitor 연동 안내](https://www.revenuecat.com/docs/getting-started/installation/capacitor)
대안은 Firebase Auth/DB 또는 자체 인증·Postgres, 결제는 StoreKit/Play Billing 직접 연동이다. 직접 연동은 공급자 비용을 줄일 가능성과 검증·웹훅·운영 부담을 비교해야 한다. 이번 설계에서 대체 SDK나 DB를 추가하지 않는다.

[Supabase 가격](https://supabase.com/pricing), [RevenueCat 가격](https://www.revenuecat.com/pricing). 스토어 수수료·세금·메일·인증·초과 사용량·운영 지원 비용은 별도로 산정해야 하므로 월 총액을 고정 견적처럼 제시하지 않는다. 운영용 요금제와 예산 한도는 별도 선택 사항이다.

## 8. 백업·개인정보·계정 삭제

운영자는 DB 백업과 별도 환경 복원 시험을 준비하고, 복원 뒤 결제 서비스 현재 상태를 재대조하여 예전 권리·중복 지급이 되살아나지 않게 한다. Supabase DB 백업에는 Storage 객체 본문이 포함되지 않으므로 파일을 저장하는 경우 별도 백업이 필요하다. 현재 게임 사진첩은 실제 사진 업로드가 아니다. [백업 범위](https://supabase.com/docs/guides/platform/backups)
앱 안에 계정 삭제 진입점을 두고 재인증 후 서버 기록·인증 연결·기기 캐시 처리와 남는 거래 기록의 사유/보존 기간을 알린다. 삭제는 스토어 구독 취소와 다르므로 해당되는 경우 관리 경로도 제공한다. 삭제 뒤 재가입·기존 구매 처리 정책은 결제 출시 전에 정하고 문의 경로를 시험한다.
계정 ID·인증 정보·게임 저장·거래 관련 식별자·서비스 제공자·보관/삭제·이전 지역을 실제 구현에 맞춰 개인정보처리방침과 스토어 양식에 반영한다. 현재 로컬 구현 초안을 서버 수집이 이미 시행 중인 것처럼 바꾸지 않는다.
리뷰어가 로그인·복원·결제 경로를 확인할 시험 접근과 설명을 준비하고 비밀은 공개 저장소에 두지 않는다. Apple 로그인 선택지·계정 삭제·구매 규칙 등은 제출 버전에 맞춰 재확인한다. [Apple 심사 지침](https://developer.apple.com/app-store/review/guidelines/)
길목에 재사용할 수 있는 것은 인증·동기화·검증 패턴이다. 공용 운영 DB·공용 구매 계정·사진/위치 업로드를 이번 설계로 결정하지 않으며 앱별 정책과 데이터를 분리한다. 길목의 실제 사진·위치는 별도 범위의 저장/개인정보 설계가 필요하다.

## 9. 통과 기준 — 아직 실행하지 않은 시험

계정 저장 기준은 무료 내부 테스트에도 적용한다. 결제·구매 복원·환불 기준은 해당 상품을 선택해 도입할 때 적용하며, 무료 시험이나 무료 출시를 위해 IAP를 먼저 구현할 필요는 없다.

| 시험 | 통과 조건 |
|---|---|
| 재설치/다른 기기 | 동일 앱 계정 로그인 후 마지막 서버 확정 revision·진행·도감 일치. 로컬 미전송 진행은 복원됐다고 표시하지 않음 |
| 기존 기록 이전 | 취소 시 서버/원본 무변경. 동의 후 응답 유실·10회 재시도해도 한 번 반영, 원본 유지, 하트 합산·유료 지급 0회 |
| 같은 기반의 두 기기 저장 | 하나 성공·하나 충돌, 양쪽 원본 보존. 선택 뒤 양 기기가 같은 revision 확인 |
| 계정 전환/늦은 응답 | A의 화면·파일·대기 요청이 B에서 노출/전송되지 않음. A 재로그인 시 A 대기만 재개 |
| 인증 연결 | Apple 비공개 이메일·Google 별도 identity·동일 이메일 공급자 조합을 시험. 증명 없는 기존 계정 저장/구매 병합 0회 |
| 오프라인/연결 단절 | 로컬 상태 표시 정확, 재연결 동일 작업 10회 재시도에도 서버 한 번 반영. 유료 구매/소비 임의 지급 0회 |
| 결제 대기/취소/서버 장애 | 검증 완료 전 지급 0회. 완료 후 중복 SDK 응답·웹훅에도 한 번 반영하고 재처리 가능 |
| 구매 복원/다른 앱 계정 | 동일 계정 권리 복원, 소비 재화 재지급 0회. 같은 스토어 계정의 다른 앱 계정에서 자동 이전 0회; 새 결제 전에 복구 안내 |
| 환불/철회·순서 역전 | 서버 재조회 결과와 앱 권리 일치. 이전 성공 알림 재전달로 재활성화/재지급 0회 |
| 서버 백업 복원/계정 삭제 | 별도 복원 환경에서 삭제 대상·결제 현재 상태 재대조. 삭제 요청 완료 및 보존 예외가 고지와 일치 |

모의 API 시험 → 실제 Android와 iPhone의 로그인/중단/전환 순으로 기록하고, 결제를 도입하면 양 스토어 시험 결제를 추가한다. Simulator·브라우저·스토어 sandbox 결과를 실기기 운영 결제 성공으로 합치지 않는다.

## 10. 유한한 진행 단계와 Owner 결정표

1. 이 설계 검토 후 첫 범위·공급자 검증 후보·무료 시험 운영 조건을 선택한다.
2. 인증 연결과 Capacitor 호환을 작은 시험으로 확인하고 계정 저장·충돌·기존 기록 이전·삭제를 구현한다. 합성 데이터부터 사용한다.
3. 실제 두 기기의 무료 플레이와 복원 기준을 통과시킨다. 개인정보/백업/문의 준비를 함께 확인한다.
4. 수익화를 도입하기로 하면 상품 한 종류와 가격·귀속/복원/오프라인 정책을 선택한 뒤 구매 검증·원장을 구현한다. 광고를 선택한 경우 광고/동의 경로를 따로 검증한다. 무료로 먼저 출시하는 선택도 가능하다.
5. 선택한 범위의 실제 기기 기준과, 결제 도입 시 시험 결제·환불·중복 방지를 통과한 후 출시 서명·심사 자료·운영 예산을 확정하고 제출을 진행한다.

| 결정할 것 | 권장 출발점 | 아직 선택하지 않은 범위 |
|---|---|---|
| 첫 검증 범위 | 계정 저장 + 무료 테스트 | 첫 출시와 동시에 결제를 넣을지 |
| 첫 유료 상품 | 신규 꾸미기 팩 한 종류 검토 | 광고 제거·하트·구독, 실제 구성/가격 |
| 공급자 | Supabase 후보의 인증/저장 시험, 결제는 상품 결정 후 RevenueCat 검토 | 공급자 확정·운영 요금제·예산 |
| 로그인/이전 | 검증된 identity + 명시적 연결, 동의한 기존 기록 하나 선택 | 게스트 허용, 계정 통합/구매 귀속 예외, 보존 기간 |

설계 선택이 코드 구현·공급자 결제·데이터 이전·스토어 출시 완료를 뜻하지 않는다. 이 문서 작성으로 SDK 설치, 서버 생성, 과금, 운영 데이터 업로드, 상품 생성 또는 스토어 제출을 실행하지 않았다.
